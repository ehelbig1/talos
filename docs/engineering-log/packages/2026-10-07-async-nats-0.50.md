# `async-nats` 0.47 → 0.50 (2026-10-07)

Backlog item, first of the transport group
(`2026-10-06-major-version-backlog.md`). Every job, result, heartbeat and
signed RPC travels on this client; 26 crates inherit it from the workspace
table. The bump is one line and needed no source change — so everything
below is behaviour, and none of it would have shown at compile time.

## Measured

A throwaway harness linked 0.47.0 and 0.50.0 side by side against a scratch
nats-server (the image the integration runner uses, `max_payload` 8 MiB as in
`deploy/nats/nats.conf`).

**Unchanged** (19 of the harness's lines are identical): publish/subscribe,
header round trip, request/reply, the `NoResponders` and `TimedOut` kinds and
their text, a queue group delivering each message once, messages of 2 MiB and
of just under 8 MiB on all five publish and request methods, and — after a
server restart — reconnecting, resubscribing, and honouring a message limit
set on a subscription before the restart.

**Changed, and each one a defect in 0.47:**

1. **A message over the server's limit.** 0.47 checked the size on plain
   `publish` only. On `publish_with_headers`, `publish_with_reply` and
   `publish_with_reply_and_headers` an 8 MiB + 1 byte message returned `Ok`,
   was not delivered, drew `Maximum Payload Violation` from the server, and
   cost a disconnect and reconnect; `request` did the same and then timed
   out. 0.50 refuses all of them at once with `MaxPayloadExceeded`, and the
   connection is untouched. The dispatcher sends every job with
   `publish_with_reply_and_headers`.
2. **A subject that is not UTF-8.** nats-server forwards arbitrary bytes in a
   subject. On 0.47, one such message arriving on a wildcard subscription
   panicked the client's connection task (`connection.rs:180`, an `unwrap`
   on `from_utf8`). After that every publish failed and every request failed
   with `channel closed`, with no event and no reconnect, until the process
   was restarted. Every client holds a wildcard subscription — its reply
   inbox — so one message from any credential allowed to publish there ends
   the controller's messaging. 0.50 drops the connection and reconnects.
3. **A server that stops answering.** The client finds a dead connection by
   pinging. 0.47 restarted the ping interval on every command the client
   itself issued, so a client busier than the interval never pinged. Against
   a frozen server (interval 1 s): an idle client disconnected after 2.2 s
   on both versions; one publishing five times a second disconnected after
   2.3 s on 0.50 and not at all, in the 18 s watched, on 0.47. A worker
   publishes a heartbeat every 30 s and pings every 60 s.

## Changed

* `async-nats = "0.50"` in the workspace table. Lockfile: that one package
  moves. The resolved features gain `server_2_14` and nothing else; the new
  `chrono` feature is off, so times stay on the `time` crate.
* Three tests, each of which FAILS on 0.47 (run there with the manifest
  pinned back) and passes on 0.50:
  * `an_oversized_job_is_refused_before_it_is_sent` and
    `a_subject_that_is_not_utf8_does_not_end_the_client`
    (`talos-workflow-engine-nats/tests/nats_client_resilience.rs`), through
    `NatsTransport` on a live nats-server — CI's integration job;
  * `a_publishing_client_notices_a_server_that_stopped_answering`
    (`…/tests/nats_client_notices_a_frozen_server.rs`), against a socket that
    completes the handshake and then says nothing — no server needed, so it
    runs in the DB-free job.

## What this changes for a workflow

A job too large for the broker used to be "sent", wait out its whole
attempt deadline, and fail as a timeout — once per retry, dropping the
controller's connection each time. It now fails each attempt in
milliseconds with
`publish_with_reply: max payload size exceeded: Payload size limit of N exceeded by message size of M`.

## Not done

* The dispatcher still RETRIES that failure up to the node's `max_retries`
  (it treats every delivery error but "no responders" as retryable). Each
  retry now fails at once, so the cost is the backoff; a job that can never
  fit is not worth a retry, and saying so is a change to the dispatcher's
  retry rule, not to this dependency.
* No test for the reconnect and resubscribe behaviour: unchanged between
  the versions, and already exercised by the integration suite.
