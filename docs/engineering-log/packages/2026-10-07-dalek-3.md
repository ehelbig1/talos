# `ed25519-dalek` 3 and `x25519-dalek` 3 (2026-10-07)

Backlog item, last of the encryption family
(`2026-10-06-major-version-backlog.md`). Ed25519 signs dispatches, worker
registration and the secret claim; X25519 is the key agreement of the sealed
secret envelope. Both move to `curve25519-dalek` 5.

A controller on one build signs and seals for a worker on another, so what
had to be shown is that the two sides still agree — which a round trip
through one version of the curve library cannot show.

## Pinned before the bump

Three tests, written and passing on the 2.x versions first, against values
produced OUTSIDE this code by Python's `cryptography` over made-up inputs:

* **An envelope sealed elsewhere opens.** X25519 between two fixed secrets,
  HKDF-SHA256 over the shared secret, AES-256-GCM under the seal's AAD — all
  done in Python — opened by the worker's real `WorkerEphemeral::open`. The
  worker's public key for its fixed secret is asserted as well. This is the
  envelope-seal fixture the two earlier encryption changes deferred.
* **It opens for no one else**: another worker id, or another execution, is
  refused.
* **The signing key agrees.** For a fixed seed: the same public key, the
  same signature over the same message (Ed25519 is deterministic), and the
  other implementation's signature verifies while a changed message does
  not.

## Changed

* `ed25519-dalek = "3"` in the workspace table and `x25519-dalek = "3"` in
  the job protocol. The lockfile gains the 3.x and 5.x crates, `ed25519` 3,
  `signature` 3 and `fiat-crypto` 0.3; the 2.x copies stay for a third-party
  crate that still uses them.
* **Key generation.** The 3.x crates take their random source by the
  `rand_core` 0.10 traits; the workspace's `rand` is 0.8, so
  `SigningKey::generate(&mut OsRng)` no longer type-checks.
  * `generate_dispatch_signing_key()` (job protocol) is now the one way a
    signing key is made: 32 bytes from the operating system's random source,
    and the key built from them — which is what `generate` does. All 55 call
    sites use it; one is production code (the operator's keypair command),
    the rest are tests.
  * The seal's ephemeral X25519 secrets come from the library's own
    `EphemeralSecret::random()` (its `getrandom` feature): the operating
    system's source, as before.
* The `rand_core` feature of `ed25519-dalek` is no longer asked for, and two
  crates' dev-dependency on `rand` — used only to pass `OsRng` to
  `generate` — is gone (the unused-dependency guard caught both).

## Checked

On the 3.x versions: the three fixture tests; the whole of the job protocol
and of `talos-envelope-seal`, and its secret-claim test against a live
nats-server; clippy; the unit suite; the DB-free binaries; lint.

## The encryption family, as it ends

`sha2`/`hmac`/`hkdf`, `aes-gcm` and the two dalek crates are each pinned by
known answers or fixtures from an independent implementation: every key
derivation, every stored-ciphertext layout, the signatures and the sealed
envelope. `sqlx` is the last item in the backlog.
