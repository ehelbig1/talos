# `governor` 0.6 → 0.10: an idle bucket no longer admits one call too many (2026-10-07)

Third of the five the backlog table missed
(`2026-10-06-major-version-backlog.md`, "Closed out, and corrected").
`governor` is the token-bucket behind every in-process rate limiter:
`talos-rate-limit` (the per-address API and webhook limiters, the global
limiter, the fallback of the Redis-backed login limiter, and the per-user
throttle on GraphQL mutations) and the embedding limiter in
`talos-search-service`. The production-only `tower_governor` layer already
used 0.10.4; these did not.

## Measured before the bump

0.6.3 and 0.10.4 in one program, each driven through the same 400 schedules
of calls (ten quotas from 1 ms to 30 s periods and bursts of 1 to 1,000,
forty seeds each, 160,000 calls) on a clock the program moves, beside a
token bucket written for the comparison in whole nanoseconds:

| | calls |
|---|---|
| 0.10.4 differs from the token bucket (verdict, or the wait it reports) | 0 |
| 0.6.3 admits where 0.10.4 refuses | 12,110 |
| 0.6.3 refuses where 0.10.4 admits | 39 |
| admitted in total: 0.6.3 / 0.10.4 / the token bucket | 149,492 / 137,421 / 137,421 |

**0.6.3 admits more than the quota.** A bucket that has been idle for longer
than it takes to refill admits its burst plus one. A limit of one call, left
alone for two periods, admits two at once. Upstream fixed this in 0.8.0
("spurious single cells being allowed through when the clock advanced"); the
39 the other way are its state running one cell ahead afterwards.

So every limiter listed above has been admitting one call more than
configured to any caller that paused first — which, for a limit meant to
slow a guesser down, is the caller it is for.

## Changed

* `governor = "0.10"` in the workspace table. The lockfile loses `governor`
  0.6.3, `dashmap` 5.5.3 and `no-std-compat`: one copy of the limiter instead
  of two.
* **The limiters now hold to their configured burst.** No configuration
  changed; the numbers in it now mean what they say.
* The two limiter constructors built the same quota from a copy of the same
  fifteen lines; that is now `quota_for`, which the test below drives.
* A refusal's wait is measured on the limiter's own clock
  (`limiter.clock()`, new in this line) instead of a clock constructed for
  the purpose on every refused request. `PerUserThrottle` no longer carries a
  second clock.

## Pinned

`a_bucket_left_idle_admits_its_burst_and_no_more` (`talos-rate-limit`): the
production quota on a clock the test moves — four configurations, each left
idle for exactly a refill, a refill and one period, a refill and fifty, and a
day, then drained; and half a refill gives half the burst back. It fails on
0.6.3 (`60 per 60s, burst 1, idle 2s`: admitted 2) and passes on 0.10.4.

## Checked

The crate's 59 tests (the sweep still drops refilled buckets and keeps active
ones), workspace clippy with warnings as errors, the unit suite.

## Stated limits

* The comparison ran on a clock it controls. The production clock is not
  exercised by it; the existing real-clock tests are what cover that.
* A client that had come to rely on the extra call after a pause will see
  one more refusal. None is known.
