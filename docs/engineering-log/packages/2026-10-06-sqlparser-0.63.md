# `sqlparser` 0.53 → 0.63 (2026-10-06)

Backlog item (`2026-10-06-major-version-backlog.md`). `sqlparser` is the
syntax tree all three SQL gates are built on, so a new release changes what
they can see. It was reviewed against the corpus recorded the same day
(`2026-10-06-sql-gates-carried-statements-and-select-into.md`,
`talos-sql-classify/corpus/`), and depends on that change: without it this
bump would have opened a hole (see the first point below).

## Measured

**Verdicts.** Of the corpus's 437 statements, 53 changed — every one from
"the parser refuses it" to something else. Nothing that parsed before is
judged differently.

* The worker, with no operation granted (the fleet's only configuration):
  52 of the 53 are refused. The one admitted is `SELECT … TABLESAMPLE …`, a
  read.
* The controller: 37 refused, that one read, and 15 it treats as writes and
  asks the write ceiling about.
* **`DELETE` and `MERGE` inside a CTE now parse.** Fifteen statements that
  are or carry a write became parseable: ten with a carried `DELETE`, two
  with a carried `MERGE`, `WITH … INSERT … RETURNING`, an `INSERT` whose
  source carries a `DELETE`, and a top-level `MERGE … RETURNING`. The
  worker's old hand-written walk named only `INSERT` and `UPDATE`, so by its
  own code it would not have refused a carried `DELETE` or `MERGE` (not run:
  that walk was deleted before this bump). The walk that replaced it never
  listed kinds, and refuses them.
* **`XMLTABLE(…)` would have gone from refused to a read.** It is on the
  denied-function list, but it has syntax of its own and 0.63 gives it its
  own node, with no name for either deny-list visitor to look up. Its only
  refusal had been that 0.53 could not parse it. Both visitors now refuse
  the node.
* The rest are statement kinds the parser has learned — `CREATE DOMAIN`,
  `ALTER TYPE`, `DROP EXTENSION`, `RESET`, `VACUUM`, `LOCK TABLE`, and
  procedural statements from other dialects. All refused; the DDL and
  session ones are named in the two lists so the refusal says what it is.

**Parse time.** 0.53 parsed nested function calls in time that doubled per
level — `abs(abs(…abs(1)…))`: 363 ms at 18 levels, 1.5 s at 20, 5.8 s at 22
(scratch harness, release build), for a 118-byte statement, with the
recursion limit not reached until 46. Both gates parse a guest's statement
before anything else. 0.63 parses 46 levels in 85 µs.
`nested_function_calls_parse_in_bounded_time` pins it.

**Nesting depth.** The recursion budget is 50 in both. The deepest that
parses, 0.53 → 0.63: derived tables 46 → 22 (a level now costs two); CTEs
47 → 46; parenthesised expressions, `CASE` and parenthesised queries
47 → 46; subqueries in `WHERE` and scalar subqueries 23 → 23. The depth pin
moves from "40 must parse" to "20 must parse", and says why.

**Long operator chains.** A statement at the 64 KiB cap that is one chain of
`AND`, `||` or `+` — a tree as deep as it is long — is parsed, walked and
dropped on a 2 MiB stack by both versions in a release build, and the real
validator on 0.63 was run the same way. In a DEBUG build the validator
overflows that stack on 0.63 (and so aborts the process). That is a hazard
of dev binaries and `cargo test`, not of what ships; it is not changed here
and has no test, because a test whose outcome the build profile decides
proves nothing.

## Changed

* `sqlparser = "0.63"` in the workspace table, default features. The
  lockfile moves `sqlparser` and `sqlparser_derive`, and gains what the
  default `recursive-protection` feature brings: `recursive`,
  `recursive-proc-macro-impl`, `stacker`, `psm`, and `psm`'s build
  dependencies. It grows the stack as the parser and the visitor descend.
* Ported in the worker's validator and the controller's handler:
  * every `SET` is one `Statement::Set` with a sub-kind; all are blocked,
    and a sub-kind a later release adds is blocked as plain `SET`;
  * a name part is an identifier or, in other dialects, a function that
    computes one. The denied-function check refuses a name it cannot read.
    Nothing the PostgreSQL dialect parses produces such a part, so that
    branch has no test;
  * `UPDATE` is a struct; `MERGE … RETURNING` returns rows;
  * the statement kinds added since 0.53 are named in the DDL and
    always-blocked lists (they were refused as unknown without that).
* Three pins that said "0.53 refuses this" now say what 0.63 does with it.
* The corpus gains four `XMLTABLE` rows (441), and the per-statement rules
  beside the snapshots look for `XMLTABLE(` in what is admitted.

## Mutation proof

The nine mutations of the gates recorded with the corpus were re-run on this
tree, with two more: the worker letting `XMLTABLE` through, and the
controller letting it through. A test fails on each of the eleven. The
worker's rule first missed its own mutation — its text check skipped any
statement containing a quoted string, which every `XMLTABLE` call does — and
was corrected.

## Not done

* The pipe operator, `FROM`-first selects and `SELECT * EXCLUDE` are still
  parse errors under the PostgreSQL dialect.
* The debug-build stack hazard above.
