# `redis` 0.27 → 1.7, and one place a Redis connection is opened (2026-10-07)

Backlog item, second of the transport group
(`2026-10-06-major-version-backlog.md`). Redis is behind login throttling,
rate limiting, replay protection, idempotency, the second-factor counters,
the module cache and the guest `cache` world.

## The change that mattered: default deadlines

`redis` 0.27 put no deadline on an async connection. From 1.0 the library's
defaults are **500 ms for a response and 1 s to connect**, on every async
connection. There is no client-wide setting; a configuration is passed where
each connection is opened. The workspace opened connections at 44 call sites
in 19 crates and passed none.

Measured with both versions against a scratch Redis: a command that takes
0.8 s returns its answer on 0.27, and on 1.7 fails after 500 ms with
`timed out` — on a multiplexed connection and on a connection manager alike.

Taking the bump as it came would have put that deadline on every Redis call,
unchosen. Two reasons it was not taken:

* **Connect, 1 s.** The workspace's floor for a connect timeout is 5 s, set
  after a cold name lookup was measured at 2.0–2.1 s inside the containers
  (it failed every client with a shorter limit). 1 s is below it.
* **Response, 500 ms.** The guest `cache` world accepts values up to 10 MiB
  and batches of 1000 keys, and the module cache holds compiled modules.
  Nothing in the workspace issues a blocking command, so nothing NEEDS a
  long wait — but nothing was measured to fit in 500 ms on a Redis that is
  not on the same host, and the fleet's Redis latencies could not be read
  for this change (the server requires a password this session does not
  hold).

### What was decided

`talos-redis` is a new leaf crate with the two openers, `multiplexed` and
`manager`, and two constants:

* `CONNECT_TIMEOUT` = 5 s. Connecting was unbounded and is now bounded, at
  the workspace's floor.
* `RESPONSE_TIMEOUT` = none — what every call site had. A caller that needs
  a deadline on one operation wraps that operation, as the rate limiter does
  (3 s).

All 44 sites call the openers. `clippy.toml` disallows the eight `redis`
constructors that open an async connection, and `make lint` checks that the
only file allowed to call them is `talos-redis/src/lib.rs`
(`lint-clippy-disallowed.py check redis`; the script learned rules with
several paths and a name instead of a structural-check number).

**Open decision.** Whether every Redis response should have a deadline, and
what, is one constant. It wants the fleet's latencies first:
`redis-cli INFO latencystats` on the live server answers it.

## Everything else, measured

The same harness ran 69 probes of the commands the workspace uses: `GET`,
`SET` with `NX`/`EX`, `SETEX`, `DEL`, `INCR`, `EXISTS`, `TYPE`, `ZCARD`,
`TTL`, `EXPIRE`, `HGET`, `EVAL`, a `Script`, and atomic and plain pipelines,
each read back as the types the code asks for. 54 lines are identical. The
rest:

* **Error kinds and text.** `TypeError` is `Parse`, `ResponseError` is
  `Server(ResponseError)`, `ExtensionError` is `Extension`, `IoError` is
  `Io`; the text lost its "An error was signalled by the server" prefix.
  Nothing in the workspace matches on a Redis error's kind or text beyond
  three places that BUILD an I/O error, which were renamed. Log lines read
  differently.
* **An empty pipeline** is now an error (`empty command`) where it was
  `Ok`. An empty ATOMIC pipeline is `Ok` on both. The workspace has two
  pipelines: one always holds two commands; the other is the guest's batch
  write, which is atomic — an empty batch from a guest still succeeds.
* Every value conversion is identical, a missing key read as each type
  included; a 6 MiB value round-trips on both.

Compile-time: `get_multiplexed_tokio_connection` is gone (it was the same
call); `ConnectionInfo`'s address is behind an accessor and its type is open
to new kinds, so the security audit's Redis-transport probe gained an
`Unrecognised` verdict, which is never reported as TLS and fails in
production.

**TLS.** The library no longer brings its own crypto provider, so a
`rediss://` connect needs the process to have installed one. With both
providers in the build, as here: with `ring` installed a TLS connect fails
as an ordinary error against a server that is not speaking TLS; with none
installed it PANICS. The controller and the worker both install `ring` as
the first thing `main` does, which predates this change. A real TLS
handshake with a Redis server was not run.

## Changed

* `redis = "1.7"` in the workspace table. The lockfile moves `redis` and
  `combine`, gains `arcstr`, `async-lock`, `event-listener-strategy`,
  `num-bigint` and `xxhash-rust`, and drops one `socket2`.
* `talos-redis`, its tests (the two deadlines shown on the wire against a
  socket that speaks enough of the protocol; both fail if an opener goes
  back to the library's defaults), the call sites, the clippy rule, the
  lint leg, and a line in `CLAUDE.md`.

## A licence the allowlist did not have

`redis` 1.x depends on `xxhash-rust` unconditionally (a value-digest
helper; no feature turns it off). It is licensed BSL-1.0, the Boost
Software License, which `deny.toml` did not allow, so `cargo-deny` refused
the bump. BSL-1.0 is permissive — OSI-approved, no copyleft, and its text is
required with source copies only, not with a compiled binary.

`deny.toml` gains an exception for that ONE crate, not an allowlist entry.
Accepting a licence is the operator's decision; it is made by merging this
change, and the alternative is holding `redis` at 0.27, whose line ended at
0.32.

## Not done

* No deadline on a Redis response (above).
* The Redis-backed suites were run against a scratch Redis; nothing was run
  against the fleet's.
