# `syn` 2 → 3 in the module macros (2026-10-07)

Second of the five the backlog table missed
(`2026-10-06-major-version-backlog.md`, "Closed out, and corrected"). One
crate declares it: `talos_sdk_macros`, the three attribute macros
(`talos_node`, `talos_module`, `talos_agent`) that wrap the entry point of
every user module and every catalog template.

So the question was not whether the crate compiles on 3 — it does, with no
source change — but whether a module built with it is the same module.

## Pinned before the bump

The macros had no test of what they expand to; the crate's tests covered one
string helper.

* Each macro is now a thin entry point over `expand_<name>`, which takes and
  returns `proc_macro2` streams and can be called from a test. The parse and
  its error path are what `parse_macro_input!` expanded to.
* Six expansions are recorded in `talos_sdk_macros/expansions/` (typed
  arguments, the default world, a doc comment and attribute carried through,
  the agent's defaults and its named provider, model and world) and compared
  token for token. Two more tests hold the world marker to the attribute and
  a non-function to a `compile_error` rather than a panic.
  `TALOS_MACRO_EXPANSION_BLESS=1 cargo test -p talos_sdk_macros` re-records.
* The recording was shown to bite: one changed call in the generated code
  fails `talos_node_expands_as_recorded`.

## Measured, end to end

Three catalog templates (`example-node` and `github-pr-reviewer`, which use
`talos_node`, and `send-slack-message`, which uses `talos_module`) built to
wasm in a scratch copy, with three versions of the macro crate:

| macro crate | result |
|---|---|
| `main` | the baseline; a clean rebuild gives the same bytes |
| the refactor above, still `syn` 2 | byte-identical to the baseline, all three |
| the refactor on `syn` 3 | same size to within one byte; different bytes |

The `syn` 3 modules were disassembled beside the baseline. In all three:
the same number of functions (284, 305, 340), the same set of function
bodies, and types, imports, memory, globals, data segments and export names
identical as written. What differs is the order the functions are laid out
in, and so the numbers they are called by. The macro crate's dependency set
is part of the hash the compiler derives names and order from; the generated
code is the same.

On `syn` 3 the six recorded expansions are unchanged.

## Changed

* `talos_sdk_macros`: `syn = "3"`. No other source change was needed.
* **Every module build compiles one crate fewer.** `serde_derive` already
  uses `syn` 3, so each module's lockfile held `syn` 2.0.119 (for these
  macros) and 3.0.6; now only 3.0.6. `syn` with `full` is among the slowest
  crates in a cold module build.
* The workspace lockfile keeps `syn` 2: other dependencies still use it.

## Checked

`make check-catalog` (all 83 templates compile through the production
manifest), `make check-catalog-fuel` (each recorded run within its declared
limit), the macro, compilation and catalog-test crates (336 tests), workspace
clippy with warnings as errors.

## Stated limits

* The function-set comparison masks function numbers, so it shows the same
  bodies are present, not that each call reaches the same callee. The
  token-for-token expansions are what cover that.
* A module recompiled after this change has different bytes for the same
  source, as after any toolchain or dependency change. Nothing compiled
  before is touched.
* `talos_agent` is used by no catalog template; it is covered by its two
  recorded expansions only.
