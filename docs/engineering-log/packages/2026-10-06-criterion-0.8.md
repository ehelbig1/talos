# `criterion` 0.5 → 0.8, and the benchmark it serves runs again (2026-10-06)

Backlog item (`2026-10-06-major-version-backlog.md`). One crate uses
`criterion`: `talos-workflow-engine`, as a dev-dependency of
`benches/scheduler.rs` (fan-out, chain and seeded-resume scheduling).

## Measured

The benchmark compiles unchanged against 0.8.2. Lockfile: `criterion` and
`criterion-plot` move, `is-terminal` and `itertools` 0.10.5 leave, `alloca`
and `page_size` arrive. All of it is reachable only from the benchmark.

Running it once, to check the bump, found that it did not run on main at
all: the `fanout/1000` case builds 1 root + 1000 leaves and the engine
refuses a graph above its node cap (500 by default), so the benchmark
panicked at "graph loads". It predates the cap. Clippy compiles a
`harness = false` benchmark; nothing ran it.

## Changed

* The benchmark's engines raise their node cap to 2,048. All eight cases run.
* `quality.yml` runs `cargo test -p talos-workflow-engine --bench scheduler`
  in the DB-free job: under `cargo test` criterion runs each case once and
  measures nothing (about 20 s locally, in the profile that job has already
  built). A benchmark that stops running now fails a pull request.

## Not done

* **Recording benchmark numbers in CI.** Shared runners are too noisy for a
  number to mean anything; the step only proves the benchmark runs.
* **`--benches` for the whole workspace.** It would also build and run every
  crate's unit tests a second time. A new benchmark target is added to the
  step by name; its comment says so.
