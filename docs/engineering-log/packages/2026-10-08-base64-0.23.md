# `base64` 0.22 → 0.23 (2026-10-08)

Fourth of the five the backlog table missed
(`2026-10-06-major-version-backlog.md`, "Closed out, and corrected"). Eleven
workspace crates use it, through two engines only: `STANDARD` (padded) and
`URL_SAFE_NO_PAD`. What they encode is sent and stored — token segments,
signatures, key material, mail bodies, and whatever a module's
`crypto::encode` returned to it — and what they refuse to decode is part of
how a token is checked.

0.23 reworked the decoder so that new SIMD engines can share it, so "the
same engine constants" was not taken as "the same behaviour".

## Measured before the bump

0.22.1 and 0.23.1 in one program, both engines, beside an RFC 4648 encoder
and a strict decoder written for the comparison:

| | result |
|---|---|
| encode: 3,083 inputs (every length to 1,024 three times, buffers to 1 MB) | identical; equal to the reference |
| decode: 36,812 texts — valid ones, and each with a character replaced, inserted, removed or appended, padding added, the last symbol made non-canonical, plus 20,000 of noise | identical: the same bytes, or the same kind of refusal naming the same position and byte |
| what 0.23.1 accepts, against the strict reference | identical on all 36,812 through both engines |

The one difference found is the wording of one error
(`Invalid last symbol 66, offset 5.` became
`Invalid last symbol 0x42 ('B') at offset 5, decoded as 0b00000001.`), and
that variant gained a field. Nothing in the workspace matches on the variant
or the text, and the function a module calls reports every decode failure as
`invalid-input`.

## Pinned

`test_crypto_base64_known_answers_and_refusals` (`talos-worker-runtime`),
written and passing on 0.22 first: `crypto::encode` and `crypto::decode`
against the RFC 4648 test vectors in both encodings, the two characters the
alphabets disagree on, and thirteen refusals — missing or extra padding on
the padded form, any padding on the URL-safe form, the other alphabet,
whitespace, an impossible length, and trailing bits that are not zero.

## Changed

`base64 = "0.23"` in the workspace table. No source changed.

## Stated

* **The lockfile keeps 0.22.1.** Six third-party crates still use it, so
  unlike the three before it this bump removes no copy; `bcrypt` had already
  brought 0.23.1 into the build.
* 0.23 adds SIMD engines behind a default-on feature named `simd-unsafe`.
  The two engines used here are the scalar ones and do not call that code.
  The feature was left on: `bcrypt` enables it for the same copy of the
  crate, so turning it off in the workspace table would change nothing that
  is built.
* The crate's own documentation says these engines are not constant-time.
  That is the same in both versions. Which call sites decode key material
  with them was not audited for this change.
