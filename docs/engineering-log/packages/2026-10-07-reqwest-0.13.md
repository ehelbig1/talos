# `reqwest` 0.12 → 0.13, and outbound HTTPS moves to rustls (2026-10-07)

Backlog item, last of the transport group
(`2026-10-06-major-version-backlog.md`). Every outbound HTTP call the
controller and the worker make goes through this client.

## What was found first

**Outbound HTTPS was running on OpenSSL.** All 26 crates that use `reqwest`
asked for its `rustls-tls` feature. But `talos-worker-runtime` enables
`oci-distribution`'s default features, which switch on `reqwest`'s
`native-tls`; Cargo merges features into the one `reqwest` both binaries
link; and `reqwest` 0.12 uses native-tls for every client whenever it is
compiled in, unless the client asks otherwise. Two call sites asked.

Confirmed in a throwaway container made from the controller image, with a
client built from the features the workspace resolved to: a TLS failure
reads `error:0A000…:SSL routines:…`, which is OpenSSL's. Not a
vulnerability: the TLS library was the image's OpenSSL (3.5.6) and the trust
store the image's CA bundle. But the manifests said one thing and the
binaries did another.

`reqwest` 0.13 forces the choice — `rustls-tls` no longer exists. The
operator chose rustls.

## Measured

One probe, both versions, run inside throwaway containers made from the
controller image (so: its CA store, its OpenSSL):

* **Against local test servers, 26 cases.** Identical: the request headers
  sent by default, HTTP/1.1, redirects followed by default and refused under
  `Policy::none()`, the redirect-loop error, gzip, `query`/`form`/`json`
  encodings, status errors, a slow response, a dropped connection, a
  truncated body, a refused connection, an address that never answers. A
  certificate from an untrusted authority, and one for the wrong host name,
  are refused by both; the same authority added as a root is accepted by
  both; a TLS 1.2-only server is accepted by both.
  Different: the WORDING of a TLS failure (`invalid peer certificate:
  UnknownIssuer` where OpenSSL said `certificate verify failed`), and two
  decode errors that now name the URL. The worker's transport classifier
  matches markers present in both wordings.
* **Against the public API hosts the fleet's modules may reach, 30 hosts**
  (Google's, Anthropic, OpenAI, GitHub and its registry, Slack, Plaid,
  Stripe, PagerDuty, Atlassian, Microsoft's mail hosts and others): an
  unauthenticated `GET /` each. Both stacks complete the handshake with all
  30 and get the same HTTP status from each.

A first run reported a name that does not resolve as a timeout on 0.12 and a
DNS error on 0.13. Run in the other order both report a DNS error: the first
lookup of a name was slow, whichever version made it.

## Changed

* `reqwest = "0.13"` in the workspace table; the feature is `rustls` in 26
  manifests. `.query()` and `.form()` are behind features from 0.13, enabled
  in the three crates that use them. HTTP/2 stays off, as it was.
* **What a client is now:** rustls, with the process's crypto provider —
  `ring`, which the controller and the worker install first thing in `main`
  — and the operating system's trust store, read by
  `rustls-platform-verifier`. On Linux that is the same CA bundle OpenSSL
  read; both runtime images install `ca-certificates`. `aws-lc-rs` is
  compiled as `reqwest`'s fallback provider and is what a test process uses.
* **`oauth2`.** Its latest release, 5.0, implements its HTTP client for
  `reqwest` 0.12 only. `talos-oauth` now sends `oauth2`'s requests itself
  (`Oauth2Http`), on the same hardened client as before; `oauth2` no longer
  depends on `reqwest` at all. It is their implementation line for line,
  except that the token response is read under the cap the rest of the file
  uses, where theirs reads without limit. The existing wire-contract tests
  of the token exchange (the exact bytes sent; redirects refused) pass
  unchanged.
* `outbound_tls_pin` in the controller's and the worker's own unit tests: a
  client built in that binary speaks TLS to a port answering plain HTTP, and
  the failure must be rustls's. Checked against the regression it exists
  for: with `native-tls` added to one crate's `reqwest` features, 0.13 also
  prefers it, and the test fails.
* The lockfile keeps `reqwest` 0.12 beside 0.13 and gains
  `rustls-platform-verifier`, `webpki-root-certs`, `wasm-streams`, two SIMD
  UTF-8 crates, and Android-only `jni` crates that no target here compiles.

## Not done

* **`oci-distribution` is still on `reqwest` 0.12 with native-tls**, so
  registry pulls still use OpenSSL and OpenSSL is still linked. Its
  successor, `oci-client`, uses 0.13; moving to it is the next change. The
  pin tests will fail that change if `oci-client` brings native-tls with it.
* **No authenticated call was made.** The probe proves handshakes and
  certificate trust, not that each integration's requests still succeed.
  After the deploy, the scheduler's own runs are the evidence: mail polling
  runs every few minutes and would fail at once.
