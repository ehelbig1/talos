# `rand` 0.8 → 0.10: bytes for a key come from one place (2026-10-08)

Last of the five the backlog table missed
(`2026-10-06-major-version-backlog.md`, "Closed out, and corrected"), and
the widest: 22 crates declared `rand`.

## What the workspace used it for

| use | sites |
|---|---|
| `OsRng.fill_bytes(..)`: a key, nonce, salt or bearer token from the operating system's source | 38, in 19 crates |
| the thread-local generator, for the 16 random bytes of a message nonce | 3 (and 1 in a test) |
| the thread-local generator, to make an RSA key in a test | 7 |
| a random `f32` for retry jitter | 1 |

Nothing shuffles, samples a range or seeds a generator from a fixed value in
production code.

## What changed in the library

`OsRng` is `SysRng` and no longer has an infallible `fill_bytes`: the
operating system's source can fail, and 0.10 makes each caller say what then.
In 0.8 the answer was built in — `fill_bytes` panicked. `thread_rng()` is
`rng()`, `gen()` is `random()`, and the traits are renamed.

So all 38 draws had to be rewritten, each to carry its own answer to "what if
the source fails".

## Changed

* **`talos-random`**, a new leaf crate: `fill(&mut [u8])` and `bytes::<N>()`,
  from the operating system's source, panicking if it is unavailable — what
  0.8 did, now written down once with the reason (a buffer the kernel did not
  fill is a buffer of zeros, and a key of zeros works). The 38 draws call it.
  It was introduced on 0.8 first, as a refactor with the workspace's tests
  passing, and `rand` was bumped behind it.
* **Three crates declare `rand` now, not 22**: `talos-random`, and the two
  that use the thread-local generator (`talos-workflow-job-protocol` for
  message nonces, `talos-worker-runtime` for a nonce and for jitter). Those
  uses are unchanged in kind: still the thread-local generator, by its new
  name.
* **RSA keys in tests** come from `rsa::rand_core::OsRng`. `rsa` 0.9 takes a
  generator of the older trait family, which a 0.10 generator is not; the
  crate's own source is switched on for tests only (`getrandom`, as a
  dev-dependency feature), so no production build changes.
* The lockfile's 0.10 copy moves 0.10.1 → 0.10.3 (0.10.2 removes a possible
  memory-safety fault in a deserializer this workspace does not use, and some
  `unsafe`). 0.8.8 and 0.9.4 stay: third-party crates still use them.

## Pinned

`talos-random`'s tests: a buffer is overwritten whatever it held; 64 draws of
32 bytes are all different; every position of a buffer is written, for
lengths from 1 byte to 70,000 (a source that fills only a prefix leaves the
rest at zero); the bits of a megabyte are balanced to within ten standard
deviations; an empty buffer is not an error.

These catch a source that is constant, short, or badly biased. They cannot
show the bytes are unpredictable; that rests on the source being the
kernel's, which is by construction.

## Checked

Workspace clippy with warnings as errors, the unit suite, the service-free
test binaries, `make lint` (the unused-dependency check is what confirmed the
19 manifests).

## Stated

* Message nonces still come from the thread-local generator (a ChaCha
  generator seeded and reseeded from the operating system), not from a system
  call each. That was the choice before and is recorded in the code; it was
  not revisited here.
* Nothing stops a new call site from using the library's source directly.
  The rule is in `CLAUDE.md`; there is no lint for it.
