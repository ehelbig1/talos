# `sqlx` 0.8.6 → 0.9.0 (2026-10-07)

Last item of the major-version backlog
(`2026-10-06-major-version-backlog.md`). `sqlx` is the database layer of the
controller: every query, the connection pools, and the migrator that runs at
startup.

Three things could go wrong without a compile error, so they were measured
first: a migrator that reads the migrations differently and refuses to start
against a database that is fine; a query cache the new macros read
differently; and defaults that moved.

## Measured before the bump

**The operator's database (read-only).** `_sqlx_migrations` holds 362 rows,
all `success`, and each recorded checksum is SHA-384 of the bytes of the
migration file with that version: 362 of 362, none applied without a file,
none unapplied.

**0.8.6 and 0.9.0 in one program** (the two libraries under different names,
against a throwaway Postgres from the pinned pgvector image):

| | result |
|---|---|
| What each reads from `migrations/` (version, description, SQL, checksum, type, `no_tx`) | equal on all 362; both equal SHA-384 of the file |
| 0.8.6 applies everything, then 0.9.0 runs over that database | nothing to do; table unchanged; 0.8.6 runs again cleanly |
| 0.9.0 applies everything, then 0.8.6 runs over that database (the rollback case) | nothing to do; table unchanged |
| The `_sqlx_migrations` table each creates | same six columns, same defaults, same primary key; same 362 rows |
| A tampered checksum / an applied version with no file / an unfinished row | both refuse, with the same error (`VersionMismatch` / `VersionMissing` / `Dirty`), whichever version wrote the table |
| The advisory lock held while migrating | the same lock (`872956014:4265677914`) |
| One of each started together on an empty database | both succeed; the 4-second migration ran once |

**The two command-line tools** over each other's databases: each reports all
362 `installed` and applies nothing.

**Defaults.** The pool's defaults are identical in the two sources. In the
Postgres connection options the differences are the fallback user name when
`PGUSER` is unset and the escaping of values passed to `.options()`, which
nothing in the workspace calls. URL parsing is unchanged.

## Pinned in the workspace

`controller/src/migrations_pin.rs`, written and passing on 0.8.6 first: the
migrator embedded in the controller holds every migration file, in strictly
increasing version order, under SHA-384 of the file's bytes; it takes the
lock; and it does not ignore an applied version it does not carry. With the
measurement above, that is what makes a controller on any `sqlx` version
accept the operator's database.

## Changed

* **`sqlx = "0.9"`.** The combined feature `runtime-tokio-rustls` no longer
  exists; 74 manifests and the integration-scaffold template now say
  `"runtime-tokio", "tls-rustls-ring-webpki"`, which is what it expanded to.
  The lockfile loses 15 packages (`md-5`, `etcetera`, the 0.48 `windows-*`
  set) and gains none.
* **SQL that is not a literal.** 0.9 takes a query's text as `&'static str`
  only; any other string must be wrapped in `sqlx::AssertSqlSafe`. Of about
  2,770 query call sites, 143 needed it: 80 in tests, 63 in production code
  (22 files). Each of the 63 was read, and carries a `// sql-safe:` comment
  saying what varies in the string:

  | what varies | sites |
  |---|---|
  | constants or literals of the same file (a column list, a batch size) | 28 |
  | a `talos_workflow_liveness` predicate (fixed text, literal alias) | 15 |
  | `SET` / `SET LOCAL`, which take no bind parameters: Uuids, a configured integer, a validated role name | 7 |
  | fixed clauses chosen by which filters or fields are set; only placeholder numbers are formatted | 6 |
  | names from the `&'static str` provider registry | 3 |
  | SQL a caller writes on purpose | 4 |

  The last four are the worker's `database` world (two sites in
  `talos-rpc-subscribers`) and the platform-admin `query_paginated` tool (two
  in `talos-advanced-repository`). The wrapper is not their control and their
  reasons say so, naming what is: the worker's validator,
  `controller_permits_data_statement`, the write ceiling and the guest role
  for the first; the handler's validation for the second.

  No site was found that writes a request's value into SQL.
* **Two helpers now take `&'static str`** instead of `&str`
  (`dependent_workflows_sql`, `archive_move_sql`): each formatted its argument
  into SQL behind a `debug_assert` or nothing, and both callers pass literals.
  The type now refuses anything else.
* **No copy on the common path.** A wrapped `String` is handed to the driver;
  a wrapped `&str` is copied. 15 production sites that borrowed a string they
  did not use again now hand it over. Three batched sweeps reuse their SQL
  across iterations and copy it once per batch (a few hundred bytes beside a
  5,000-row `DELETE`).
* **The query cache** (`.sqlx/`) was regenerated with the 0.9 tool against a
  database migrated from this checkout. 23 files changed, each only by a new
  `origin` field per column (the table and column it came from); no type and
  no nullability moved. 9 files were removed: entries for queries that were
  macros once and are runtime queries now (each checked against the tree).
  50 remain, for 59 macro uses.
* **The command-line tool is pinned to the library's version.** CI installed
  it with no version, so since May it had been running 0.9.0 against a
  workspace on 0.8.6, while the controller image pinned 0.8.6. Now:
  `sqlx-cli@0.9.0` in the three CI steps, `--version 0.9.0` in
  `controller/Dockerfile`, and `scripts/check-sqlx-cli-pin.py` (in
  `make lint`) compares both with `Cargo.lock`.
* **The image's tool is built with the Postgres driver and rustls only**
  (`--no-default-features --features postgres,rustls`). The default features
  add the MySQL and SQLite drivers and link OpenSSL. Built inside a container
  from the current controller image: it compiles, links neither `libssl` nor
  `libcrypto`, and — beside the image's 0.8.6 tool — reads the scratch
  database's 362 migrations with `sslmode=disable` and over TLS with
  `sslmode=require`; both refuse a self-signed certificate under
  `verify-full`.

## New checks

* `scripts/check-sql-safe-reasons.py` (`make lint`): every `AssertSqlSafe(` in
  production Rust has a `// sql-safe:` reason on or directly above it. Test
  code is not read.
* `scripts/check-sqlx-cli-pin.py` (`make lint`): the tool's version in the
  image and in CI equals the `sqlx` version in `Cargo.lock`.

## Stated limits

* A reason is prose. The check proves one was written next to the code, not
  that it is true.
* `sqlx-cli` 0.9.0 ships a lockfile, and `--locked` uses it. Four of its
  entries have since been yanked from crates.io (`chacha20` 0.10.0,
  `crypto-bigint` 0.7.3, `der` 0.8.0, `spin` 0.9.8); with the features above
  only `chacha20` is compiled. No advisory names any of them. The alternative,
  dropping `--locked`, lets every image build resolve the tool's dependencies
  afresh; the pinned build was kept.
* CI installs the tool as a prebuilt binary through `cargo-binstall`, which
  for this crate downloads from QuickInstall, a third-party build service
  (signature verified by `cargo-binstall`). Unchanged here.
* `query_paginated` decides that caller SQL is a read by text rules (starts
  with `SELECT`, no `;`, no comments, a table blocklist), on the primary
  pool, outside a read-only transaction. It is platform-admin only. Not
  changed here.
* A developer's own `sqlx` tool is not checked. The two versions agree on
  migrations; the query cache should be regenerated with 0.9.0.

## Deliberately not done

* The integers and constants formatted into SQL (`LIMIT {SWEEP_BATCH}`) were
  not turned into bind parameters. That would change the statement text of
  every batched sweep in a dependency change, for strings no request reaches.
* The runtime and TLS features were not moved into the workspace table: the
  rule is that features stay with the crate that needs them.
