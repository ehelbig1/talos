# `totp-rs` 5.7 → 6.0 (2026-10-06)

Backlog item, second of the authentication group. `totp-rs` computes the
six-digit codes of two-factor sign-in; one crate uses it,
`talos-totp-2fa`.

## What 6.0 changed

An API rewrite: `TOTP::new(...)` became a `Builder`, `Secret` is no longer a
`Raw` / `Encoded` enum, `generate` returns a `Token`. It ships the 5.x names
as deprecated aliases behind a default `migration` feature. The workspace
was ported to the new API and the entry turns that feature off, so the old
names cannot come back.

## Measured before porting

A throwaway harness ran the code path as written against 5.7.2 and the
ported one against 6.0.0, side by side — 3,465 comparisons, 0 differences:

* encoding a 20-byte secret to base32 (203 secrets);
* the code for each of those secrets at 16 instants, including the epoch,
  step boundaries, and times past 2^32 seconds (3,248 pairs);
* 14 spellings of a stored secret: as stored, lower-case, padded, spaced,
  dashed, with a trailing newline, with invalid characters, empty, and
  lengths of 80, 120, 128 and 512 bits. Both accept exactly the same ones:
  upper-case unpadded base32 of at least 128 bits.

Both reproduce the RFC 6238 appendix B reference values.

## Changed

* `talos-totp-2fa`: five call sites ported. Every parameter (SHA-1, six
  digits, 30-second steps) is still stated explicitly, though they are the
  builder's defaults, because the same values are written into the
  enrolment URL.
* `verify_code` now calls `verify_code_at(…, now)`, the same check with the
  clock passed in, so the acceptance window can be tested.
* Three controller test binaries each built "what the authenticator app
  shows" for themselves; they share `common::authenticator_code` now.
* Lockfile: `totp-rs` and `constant_time_eq` (0.3.1 → 0.4.2) move. Nothing
  is added.

## The tests that did not run

`test_generate_secret`, `test_generate_backup_codes` and `test_verify_code`
were `#[ignore]`d — they built a database pool outside a runtime and could
not run. So no unit test exercised secret generation or code verification;
only the controller's database suites did, end to end and at the current
time only. Replaced by five that run: the secret's shape, the backup codes,
the RFC 6238 reference codes through the service's own verifier, the
acceptance window, and refusal of malformed or short secrets.

## Mutation testing

The window decides whether a second factor is accepted. Seven mutations of
`verify_code_at`, each caught by
`a_code_is_accepted_for_its_own_step_and_one_either_side`: no previous
step; no next step; two steps back also accepted; two steps ahead also
accepted; the comparison always true; a prefix of the code accepted; only
the current step.

## Stated limit

The window test pins this crate's arithmetic (one step either side). It does
not test that the server's clock is right.
